# Правила работы над NOTA

## Ветки и согласование выпуска

- Разработка ведётся в `develop`. Основная опубликованная ветка — `main`, не `master`.
- Перед изменениями проверять ветку и рабочее дерево. Сохранять изменения пользователя, не откатывать их. Не публиковать обычные доработки автоматически.
- Команда пользователя «готовим релиз» (или аналогичная) означает подготовить конкретный выпуск для согласования, а не сразу публиковать.
- Для подготовки прочитать этот файл, `release.json`, `CHANGELOG.md`, проверить актуальные ветки и теги после `git fetch origin --tags`, изучить изменения `main..develop` и незакоммиченные доработки. Не включать секреты, записи микрофона и временные файлы.
- Номер выпуска: `YYYY.MM.DD.N`, дата по Europe/Moscow, N — следующий свободный положительный номер выпуска за этот день. Тег: `vYYYY.MM.DD.N`. Существующие теги не менять и не переиспользовать. Проверять и теги, и историю. Версия в `release.json` совпадает с первой записью `CHANGELOG.md`. Версия npm-пакета не является версией сайта.
- Собрать все предназначенные для выпуска изменения в `develop`, обновить номер и текст, выполнить `npm.cmd run test` и `npm.cmd run build -- --base=/NOTA/`. Устранить ошибки до запроса согласования.
- Показать пользователю предполагаемый номер, точный пользовательский текст истории и результат проверок. Дождаться явного подтверждения. Подготовка, commit в develop и локальная сборка не требуют отдельного согласования; merge/push в main и публикация требуют подтверждения конкретного выпуска.
- Если пользователь меняет текст, учитывать его редактуру и снова показывать окончательный вариант. Если код или содержимое выпуска изменились после подтверждения, заново согласовать изменившийся выпуск.
- После подтверждения: закоммитить одобренные изменения, проверить отсутствие неожиданных изменений main, выполнить merge develop в main (предпочтительно `--no-ff`), поставить аннотированный тег на итоговый commit main. Отправить main и этот тег совместно (`git push --atomic origin main <tag>`), а также актуальный develop. Не использовать force push.
- Push в main запускает `.github/workflows/pages.yml`: тесты, сборку для `/NOTA/`, публикацию GitHub Pages. Не запускать второй workflow без необходимости. Проверить результат именно этого запуска; не заявлять об успешной публикации, пока результат не подтверждён. Если нет доступа к статусу, явно сообщить это.
- После выпуска вернуть рабочую ветку на develop и включить в неё итоговый merge из main, чтобы следующий выпуск начинался с опубликованной версии. Не удалять develop.
- Если дата меняется, не менять уже согласованный номер без обсуждения. При конфликте тегов, новых изменениях main или merge-конфликтах остановить публикацию, подготовить согласованный результат заново.

## Пользовательская история обновлений

- Единственный редактируемый источник текста — корневой `CHANGELOG.md`. Пользователь вправе самостоятельно менять его. Перед подготовкой выпуска перечитывать файл и сохранять ручные правки.
- Новые версии помещать сверху. Формат: `## YYYY.MM.DD.N`, разделы `### Новое` / `### Исправления` и пункты `- текст`. Без HTML, вложенных списков и сложного Markdown; текст отображается как обычный безопасный текст.
- Писать по-русски, кратко: новые возможности, заметные улучшения, исправления пользовательских проблем. Не перечислять внутренний рефакторинг, файлы, зависимости и команды сборки.
- Не придумывать старые выпуски. Первоначальная запись описывает заметные накопленные изменения; наличие записи и номера локально не означает, что выпуск уже опубликован. Источник факта выпуска — тег и успешный Pages deployment.
- Исправление старого текста также требует новой сборки сайта. Не перезаписывать существующий тег. Доставлять правку через очередной согласованный выпуск.
- Футер показывает номер из `release.json` и открывает всю историю. `nota-last-opened-version` хранит последнюю посещённую версию, `nota-changelog-read-version` — просмотренную историю. При первом посещении точки нет; при новой версии точка остаётся до открытия истории. Перезагрузка не должна снимать отметку непрочитанного обновления.
- При работе над интерфейсом сохранять мобильную компоновку, управление касанием и доступность с клавиатуры. Проверять, что модальные окна приостанавливают упражнения и не запускают действия по глобальному Enter.
